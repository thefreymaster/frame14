# CLAUDE.md

Guidance for Claude Code in this repository. It describes how Frame14 works now and the rules to keep; the history is in `frame14/CHANGELOG.md` and git. `frame14/src/CLAUDE.md` holds the football subsystem's own invariants.

Frame14 is a Home Assistant add-on: a dashboard for a 1600x2400 portrait Android tablet on the kitchen wall (the **frame**, in Fully Kiosk Browser) and for phones and desktops (**remotes**). Everything lives in `frame14/` (the add-on folder); commands below run there.

## Commands

```bash
npm install          # Install dependencies
npm run dev          # Vite dev server (port 3000, proxies /api and socket.io to :4000)
node index.js        # Express server (port 4000)
npm run build        # tsc -b (the app, vite.config and the tests) + Vite build + scripts/precompress.mjs
npm run lint         # ESLint — must stay at zero errors and zero warnings
npm run preview      # Preview the production build
npm test             # Vitest, client + server projects, once
npm run test:watch   # The same, re-run as files change
npm run test:e2e     # Playwright — `npm run build` first; `npx playwright install chromium` once
npm run stub         # The stub Home Assistant alone, on :8310 (STUB_PORT to move it)
```

Full-stack development: `npm run dev` and `node index.js` together.

## Process and releases

- **Every user-visible change gets a test with it** (a lib a unit test, a route a supertest one, a page an e2e spec or a step in one) and the checks must be green. Show a new test fails without the fix when it can (revert the fix, run it, put it back) — a test that can't fail proves nothing.
- `npm run lint` stays clean; fix the code rather than suppressing a rule. The `react-hooks` rules are the React Compiler's own checks — a component that fails one is one the compiler skips.
- **The user pushes to main directly until 1.0.0** (not yet: "I'm not ready for 1.0.0"). Commit or push only when asked; work on a branch and fast-forward main when told to push. The 1.0.0 plan: the "Protect The Main" ruleset (already: no deletion, no force push) gains a pull-request rule (no approvals — one maintainer — any merge method) and three required status checks — "Lint and build" (build.yml), "Unit tests" and "End-to-end tests" (test.yml), GitHub Actions' app id 15368, branch not required to be up to date. Ruleset changes are the user's to make (an agent's attempt was blocked).
- CI: `.github/workflows/build.yml` (lint + build, Node 24), `test.yml` (`unit`; `e2e` with `npx playwright install --with-deps chromium`, the report uploaded on failure), `release.yml` (on a push to main, publishes `v<version>` with the CHANGELOG section as notes when that release doesn't exist yet; a push without a bump does nothing).

### Changelog (every user-visible change)

Home Assistant renders `frame14/CHANGELOG.md` in the add-on's Changelog tab, and the section is also the GitHub release's notes.

1. Bump `version` in `frame14/config.yaml` (semver: patch for fixes, minor for features). Unrelated requests in one sitting may share one version (the user's word), one bullet each.
2. Add `## <version>` at the top — exactly config.yaml's string; HA matches on it.
3. Bullets `- Added:` / `- Changed:` / `- Fixed:`, user-facing (what changed on screen or in config, not which file), readable on their own. Skip internal refactors.
4. Say so explicitly when a `config.yaml` option is added or renamed.

Gotchas the suite has hit:
- The page under an open drawer is `aria-hidden`: getByRole can't see it — locate by attribute (`[data-light-entry][aria-label="…"]`).
- A dial's number is a NumberFlow that names itself through ElementInternals; getByText / getByRole don't see it — poll `dialReading`.
- PageTransition's scale-in (and a modal's) draws every box a little short and off: wait for the animations' `finished` (or poll) before measuring.
- The launch splash covers the page for about a second after a route mounts; a locator's click waits for it, a `page.mouse` gesture doesn't — `await splashGone(page)` first.
- zag machines (Collapsible, Switch, Slider) change state a tick after the event: `waitFor` / poll. A controlled Switch's hidden input can lag its control under act; read the control's `data-state` — and before clicking a switch that has just turned on by itself, wait for the input to be checked too: a click while it still says off turns it "on", a change to nothing, and nothing happens (NotificationsBoard.test failed that way on GitHub once). A slider thumb is found by its `aria-label` attribute (its aria-labelledby points at nothing; it is `visibility: hidden` in jsdom).
- The React Compiler memoises: a static mock of `useEntity` doesn't re-render a tile — mock it as a small store the components subscribe to.
- jsdom has no layout: no tabbability (focus traps land on the content — check focus in e2e), no rects (mock `getBoundingClientRect`).
- Playwright's touchscreen only taps; a swipe is CDP `Input.dispatchTouchEvent`. Safe-area insets: CDP `Emulation.setSafeAreaInsetsOverride` (index.html has `viewport-fit=cover`).
- zag's presence hears a modal's exit animation end only a frame after the close; a test that finishes the animation sooner leaves the closed modal in the DOM.
- Rebuild after bumping config.yaml's version, or every page of the run reloads itself once and then shows the "new version" toast.
- A page the service worker controls makes its requests through it, and `page.route` never sees them (sw.js claims its clients, so that is every page a moment after its first load): a test that answers a request itself runs under `test.use({ serviceWorkers: "block" })` (control.spec's new-version test, which answers /api).
- Notifications: the headless shell says `Notification.permission` is "denied" whatever was granted, so notifications.spec runs on `channel: "chromium"` (installed with it). It fakes PushManager with a subscription at the stub's push service and keys it holds, and decrypts what arrives (http_ece); `ServiceWorker.deliverPushMessage` (CDP) drives sw.js.
- On the desktop project /home is fitted (0.171.0): a card may be cut or folded, its hidden rows `inert` and under its More button — `toBeVisible` still passes for a clipped element, a click doesn't. Ask for `quietHouse` first, click where the card is shown (`{ position }`), or test the packing alone in a window under 560px tall, which isn't fitted. And a taller window fits no more above about 900px: the type grows with it.
- A locator's click waits for the element itself to be what takes the pointer: one with `pointer-events: none` (Board's arrow) or under a stretched tap target never is — click its box's middle with `page.mouse`.
- A module that remembers a time (lib/haptics' last tick) needs a fresh module per case under fake timers: the fake clock starts over, and "a moment after the last one" is true of every case's first call.
- Playwright's WebKit is how the iPhone's haptic labels were checked (not a project: a script, with the WebKit env) — it has no `navigator.vibrate`, so the path runs as on the phone; in the suite Chromium stands in, with `navigator.vibrate` deleted in an init script.
- A collapsible Board clips its body: Chakra's `Collapsible.Content` is `overflow: hidden` always, open too. Shadows and focus rings live in the body's padding and are fine; whatever must leave the card isn't — a row dragged out of the Navigation card vanished at the card's edge until its drag was held to the list (0.172.0). Check for that before making a card collapsible.
- Chakra quirks: SimpleGrid takes `templateColumns` or `columns`, never both (an undefined templateColumns still overrides columns' template); a `Tabs.Content` given `display: flex` needs `&[hidden]` set back to none.
- Anything that reads html's `data-safari-bar` reads it at render, not module load (main.tsx sets it after the modules run).
- A token's value is resolved at the root, not on the element that wears it: one that reads a variable the element sets (`var(--shadow-color)`, which a badge's outline variant sets on itself) is invalid there, and the property it is given to computes to nothing — an outline badge lost its outline in every palette that way until embossed.spec caught it. Where a style must read the element's own variable, write it in the recipe under the palette's condition (`_embossed`), not in a token.
- `test.skip()` called part-way through a test reports the whole test skipped, its earlier assertions with it: `return` instead.
- An animation's facts are read from the running animation, not the stylesheet: `el.getAnimations()[0].effect.getKeyframes()` for what it changes, and `animation.pause()` + `currentTime` to put it at a moment and measure (climate.spec's wisps). jsdom has no `getAnimations` at all — a component that calls it needs it stubbed (PowerFlow.test).
- The speed test's figures over loopback are whatever the machine does (10 Gbps and more): a spec holds the shape of a run — the phases, a figure's form, that bytes moved — never a speed. Unit tests drive `runSpeedTest` through a made-up `SpeedTransport` on fake timers (which fake `performance.now` too).

Locally Playwright's Chromium needs `LD_LIBRARY_PATH` at the preview tooling's extracted libs (`~/.cache/frame14-ui-tools/chrome-libs/root/usr/lib/x86_64-linux-gnu`, the lib folder, not chrome-libs itself).

## Architecture

**Client** (`src/`) — Vite + React 19 + TypeScript, compiled with the React Compiler (`babel-plugin-react-compiler` via `@rolldown/plugin-babel` and `@vitejs/plugin-react`'s `reactCompilerPreset`, in vite.config.ts and vitest.config.ts alike). react-router 8, TanStack Query, Chakra UI v3. TypeScript stays at 6.x (typescript-eslint's peer range) and `@types/node` at 24 (the runtime). Entry `src/main.tsx`: Provider (Chakra + colour mode) + QueryClientProvider + Toaster. `dist/` is served by Express.

**Server** (`index.js`) — Express 5 + Socket.IO, plain JavaScript (ESM). `config.js` reads credentials, `entities.js` the entity config, `routes/*.js` are mounted in `index.js`, `openapi.js` documents them (Swagger at `/api/docs`). One persistent WebSocket to Home Assistant (`ha-socket.js`) holds the state cache and fans states out to Socket.IO rooms.

**Docker / add-on build** — the Home Assistant host builds the image. The builder runs `npm run build` under `NODE_OPTIONS=--max-old-space-size=1024` (`tsc -b` over src + tests needs ~1 GB; when it runs out again, raise the cap — the user prefers that to splitting the typecheck out). The runtime stage copies the server's root files **by name** (`COPY index.js config.js entities.js …` plus `routes/`): a new root module must be added there or the add-on dies on start. `npm install --omit=dev` brings the server's deps (`@mdi/svg` among them).

The add-on options are config.yaml's snake_case names (`light_entities`, `climate_names` as a list of `{ entity, name }`, `printer_status_entity`, …), mapped in entities.js. Nothing about the house is hard-coded: a helper or list left empty turns its feature off, and every entity option is optional (`str?`; options.json is read whatever it holds). **A feature without its entities is left out everywhere** (the user's rule): `lib/features` (`featuresOf(config)`, `useFeatures`) decides from /api/entities — lights, climate, fans, solar (both power-now sensors), circuits, energy (either), weather, printer, vacuum, cameras (a camera, the printer or a vacuum), football, photos, unraid, account (`cloudflare_access_team`; /api/entities' `account`) — and the nav entries' `feature`, Settings' Navigation rows, a remote's Views tiles, HomeOverview's `cards` (a card left out isn't on the board, even while arranging), the Energy page's tabs and Now card, and the router's `RequireFeature` (a visit goes Home once the config has loaded) all read it. Until the config loads every feature but Unraid and the account counts as set up (FEATURES_UNTIL_LOADED), so nothing flickers; a data hook asks only once it knows (`useFeatureData`: `enabled`, and `waiting` keeps the placeholder). A new feature gets a key there and its option made optional. config.yaml's defaults are this house's values, so an update needs nothing set (the Supervisor merges new defaults in).

- `light_areas`: Home Assistant areas whose lights are all included (ha-areas.js); the Lights page groups everything by room.
- `scenes` (`scene_entities`, 0.165.0): the scenes, scripts and automations the Lights page's Scenes card runs, in the option's order; names and icons are Home Assistant's. No id is in the code — the house's movie-mode automation is config.yaml's default, like every other option's ("configured as usual from the configuration yaml, not hard coded into the app"). Scenes alone keep the Lights feature (lib/features).
- `climate_names` labels a thermostat in place of its `friendly_name` (the LocalThings Samsung entities are named after their devices); both `routes/climate.js` and `mapClimateState` (useClimate) apply it. Either name is drawn without the word AC (0.169.2, "Remove the word AC from the names": lib/hvac's `displayClimateName`, at the tile, its label and the dialog's title — the route and the config keep the word).
- `internet` (`internet_entity`): a binary sensor, `on` while the internet is up (Ping); off, the Home weather card (each layout's first card) shows the Offline alert. Empty watches nothing.
- `printer` is the status sensor: ha-bambulab's `sensor.xxx_print_status` or Bambuddy's `sensor.xxx_status`. The suffix picks the integration and every sibling entity is derived from the prefix (`src/lib/printerEntities.ts`, mirrored by `printer-entities.js` — keep them in step). Empty disables the printer.
- `albums` (`immich_album_ids`): the Immich albums the frames may play, served by Home Assistant's Immich integration with HA_TOKEN (photos.js) — no Immich address or key of the add-on's own since 0.162.0 (`immich_url` / `immich_api_key` and the `album_entity` input_select before). Empty, `PHOTOS_ENABLED` is false and Photos is left out. The pictures come from HA's `/immich/…` view, outside `/api`, so photos need `ha_url` to be HA's own address.
- Server-kept state (screen.json, theme.json, photos.json — the frames' album —, people.json — who was signed in) lives in `FRAME14_DATA_DIR`, else the add-on's `/data`, else `.data/` here (gitignored).

- **Press** (0.170.0, "I want the button press to feel more like a real life button like it depresses when pressed … on a wall mounted tablet it's not great"): **a press is `data-pressing`, never `_active`**. lib/press's `watchPresses` (started in main.tsx) tracks the pointer on the document and marks whatever pressable is under it (`PRESSABLE`: buttons, `role` button / tab / menuitem, links, a switch's and a segment's label, `[data-pressable]`; the innermost one alone, never a disabled one) from the moment of contact — Chakra's buttons answered only a hover, which a touch never is, and the browser's own `:active` comes late on a touch screen (Blink sets it once a touch has proved to be no scroll — for a quick tap, as the finger leaves; read from its source, not measured on the frame). It is held MIN_PRESS_MS at least, so the quickest tap goes all the way in; a touch where something can scroll waits SCROLL_WAIT_MS first (as iOS and Android do — a swipe from a tile is the page's, and `pointercancel` says so before the tile has moved), and a tap quicker than the wait shows as it ends. Space and Enter press the focused thing. The look is `pressable(depth, { shade, also })`: smaller (PRESS_SCALE: button 0.93, tile 0.96, a whole card 0.985 — the `scale` property, so it composes with a transform), in fast (PRESS_IN_MS) and back on a spring (PRESS_OUT_MS), and shaded along the top edge by an `::after` wearing the `press` shadow (none in Embossed, where a held button wears the recess instead: `held`, whatever else the element wears while down) unless there is no face to shade (`shade: false`: ghost and plain buttons — a ghost takes its hover fill instead —, tabs, segments, whole cards). It is on the button recipe, the tabs' trigger (both navs' entries) and a segment group's item in provider.tsx, and in the `css` of the tiles and the hand-made buttons; a new pressable thing takes it there. Two rules it brings: **an element's own transitions go in `also`** (CSS has one transition list an element; `pressable` writes the longhands, and a `transition` prop beside it would drop the press's), and **a shaded button must be positioned** — the shade lies over the nearest positioned ancestor, so on a static button it darkened someone else's box (the sheets' close buttons, in their titles' rows, were `position="static"`: they are `Modal.CloseTrigger inRow` now, in flow and still positioned; press.spec sweeps every page for another). - **Haptics** (0.170.0, "use the vibration engine on iPhone and android tablet to give some quick feedback like switches do on iPhone"; lib/haptics): a tap on anything pressable ticks, on the click — so a swipe never does, nor a hold's swallowed release. Where there is a Vibration API (Android: a phone, and the frame if the tablet has a motor and Fully Kiosk lets the page at it — not verified on the wall) `hapticTick` runs it for TICK_MS, once for the two clicks a label and its input make. **An iPhone has no such API, and no call at all**: what ticks there is a real switch (`<input type="checkbox" switch>`) toggled by a real tap — a scripted `label.click()` stopped ticking in iOS 26.5. **That part is the `ios-haptics` library's** (0.170.1; the user, of 0.170.0's own code for it, which ticked on the phone: "It does work with your implementation but I'd like to use a maintained library"): its `hapticTrigger(button)` lays an invisible `<label data-haptic-trigger>` holding a hidden switch as the button's last child — the tap lands on the label, bubbles to the button as its click, and the label hands its switch a trusted click, which the library keeps from bubbling back. How Safari is made to tick is the library's to keep up with — **don't rebuild it here**, update the dependency. What is ours is where it goes: `watchHapticTriggers`, only where `ticksThroughSwitch` (an iPhone or iPad, no `navigator.vibrate`), calls it for everything pressable on the page and each that arrives (a MutationObserver; React rewriting a button's text takes the label out, and it is put back): buttons, a menu's items, a segmented control's segments and whatever has `role="button"` (0.171.0, of the nav's More menu on a phone: "These menu items don't have haptics on click" — buttons alone before). Not a real switch, which ticks by itself, nor a link — inside one the label takes the click over and the link goes nowhere — nor a trigger that holds pressable things of its own (a card that is one button with buttons in it: the label would lie over them; one arriving later takes the card's label away). A segment is a `<label>` round its radio, and with the library's label inside it the outer one no longer hands the radio the click (a label does nothing for a click on something interactive inside it): `handOver` clicks the radio for it. Three things the library leaves to the app, all in lib/haptics: its label has no `z-index`, and ours gives it 1 (under the button's own `::after` the tap would land on the button and nothing would tick); a disabled thing's label is `display: none`; and the library makes a static button the label's containing block, which Board's collapsible header must not be — it stretches its tap target over the header with a pseudo-element and says so with `data-stretched`, so its inline `position` is put back and the label stretches the same way. A handler that calls `preventDefault` on the click stops the label's hand-over, and so the tick — a hold's release, rightly. ui/switch.tsx's inputs carry `switch` too, so Frame14's own switches tick by themselves. **None of the iPhone side can be felt from here** (Playwright's WebKit shows the switch toggled by a trusted event, once a tap, and the taps still the buttons' — not a tick); it rests on how Safari happens to work, and if a release closes it the taps go quiet and nothing else changes. - **Start-up** stays cheap: persisted queries restored before the first render, `sw.js` cache-first for hashed files, precompressed `immutable` assets, WebSocket first, a burst of states applied once per frame.
- **PWA**: `public/manifest.json`, icons from RealFaviconGenerator's set (replace it whole; its `site.webmanifest` is unused). The manifest link keeps `crossorigin="use-credentials"`: behind Cloudflare Access a cookieless fetch gets the sign-in redirect and Chrome offers no install.
- **Animations** name Chakra's own keyframes (`spin`, `pulse`, `ping`, `bounce`, `fade-in`, …) or emotion `keyframes` defined beside the component; a name defined nowhere fails silently (the fan icons stood still from 0.50 to 0.157, naming a deleted `fan-spin`). Stop them under `_motionReduce`.
- **Hand-drawn graphics** take their colours from tokens: ThermostatDial (the climate, fan and light dials), the analog clock, the football score bug, the energy charts (TodayPowerChart, TodaySparkline, EnergyHistoryChart, PowerFlow — no chart library), the Halloween scene. Team colours are data.
- `src/components/ui/` holds Chakra CLI snippets (`npx @chakra-ui/cli snippet add <name>`), locally changed: slider.tsx's marks have no inset along the track (they sit under the thumb's centre); toaster.tsx gives every toast a close button and its type's palette, and places them bottom-end, 1rem in, above the portrait bottom bar while it shows (`--toast-bottom` on the group, read by zag's `offsets`).

## Design constraints (the frame)

The frame is a **1600x2400 portrait LCD**. Design portrait-first and check that aspect: in portrait `vmin` is the width, so anything sized in vmin side by side competes for the short axis — stack down the long axis and re-flow with `@media (orientation: …)` (LandscapeNav, PageShell and FootballScoreboard do). Fill the height with content scaled to match, not stretched blocks behind small text. The OLED-era rules (black page, no borders, burn-in) don't apply. Font: Chakra's system stack; the Halloween page alone loads Creepster.

Fully Kiosk settings the frame needs: "Enable JavaScript Interface" (Advanced Web Settings) and "Prevent Device from Sleep while Screen Off" (or the socket drops and `screen on` never arrives).

## Component rules

- Every React component in its own file under `src/components/<Name>.tsx` (or a subfolder). Route files compose components and define no sibling components inline.
- Small helpers used by one component stay in its file; shared ones go in `src/lib/`.
- A stable `EMPTY` module constant for empty id lists handed to `useEntities` (a fresh `[]` re-subscribes).
- Key per-entity controls by entity id (their local state follows HA except what's under a finger).

Invariants:
- `callService` returns `false` for a call it won't send, else `sendServiceCall`'s promise, which never rejects (the process exits on an unhandled rejection).
- Home Assistant answers `automation.trigger` only once the automation's actions have finished, so for an automation `sendServiceCall`'s timeout counts as run (`slowIsRunning`), not refused; a scene or script that doesn't answer in SERVICE_TIMEOUT_MS is still a failure. `callService`'s second argument (`timeoutMs`) is the tests' — index.js passes the payload alone.
- Assist pipeline runs are subscriptions: `pendingSubscriptions` is checked before the entity_id guard in the event branch, or every pipeline event is dropped.
- The media watcher routes to /marquee only for `media_content_type: movie` and hands the panel back when playback rolls into an episode or live TV. `TRANSIENT_VIEWS` (football, marquee, halloween, blank) are never written to the route helper; the motion watcher wakes the frames onto the saved route but leaves a transient view other than blank alone.
- Today's energy totals are the change in the lifetime meters since the end of yesterday (the inverter's "today" sensors drift); monthly / yearly days are differences of end-of-day lifetime readings (the statistics `change` type is corrupted by counter resets).
- The weather routes fail only when the current-conditions entity does; a failing forecast leaves its lists empty.
- The speed test's page ends every transfer by aborting its requests, so a caller leaving midway is the normal case for `/api/speedtest/download` and `/upload`: neither may throw or emit an unhandled error (the process exits on one). The download is a `pipeline`, whose callback swallows the premature close; the upload has only `data` / `end` listeners (Node raises a request's abort as an `error` only where one is listened for). speedtest.test.js cuts both short and pings after.
- `startHaSocket(io, hooks)`: `onNotify(data)` on a `frame14_notify` event (NOTIFY_EVENT_ID; an automation's `event:` action — index.js hands it to push.js; subscribing to a custom event takes an admin's token), `onPrimed` after each connect's priming and `onRegistryChanged` on registry events (REGISTRY_EVENT_IDS) — index.js wires both to ha-areas.js, which refreshes a second after an event — and `lights`, the lights a page may call (ha-areas.js's lightsConfig; a hook rather than an import, since ha-areas.js imports ha-socket.js).


## API endpoints

- `GET /api` — health: `ok`, `version`, `assistPipeline`.
- `GET /api/entities` — the entity config with `lights` grown by the rooms, `rooms` (each with its `cameras`), `photos`, `unraid`.
- `GET /api/icon/:name` — one MDI SVG from `@mdi/svg` (immutable a year); 400 for a non-name, 404 for an unknown one.
- `GET /api/software` — `installed`, `repoUrl`, `update` (the add-on's update entity found by its `title` = ADDON_NAME: `installed`, `latest`, `available`, `inProgress`, `releaseNotes` — the latest version's CHANGELOG section via `update/release_notes`, cached per version). `POST /api/software/install` (`update.install`; 202 / 409 nothing newer / 404 no entity / 503 HA down). `POST /api/software/check` (Supervisor store reload via `supervisor/api` — an admin's command — then `homeassistant.update_entity`, then the GET's answer with `checkedAt`).
- `GET /api/account` — `{ enabled, user, people }` (no-store): `enabled` with `cloudflare_access_team`, `user` `{ email }` when Access signed the caller in, else null, `people` everyone signed in (`email`, `device`, `online`, `lastSeen`) — for a caller who is named; anyone else gets a 200 with an empty list, never a refusal. `PUT /api/account/alias { email, device, alias }` (0.173.0) gives a row of that list its alias, kept by the server and sent to the `signed-in` room; `""` or null takes it away; the GET's answer back. Any named caller, any row; 403 for a caller Access didn't name (the one refusal here: there is no row of theirs to speak of), 400 not that shape or no alias, 404 no such row or no team.
- `GET /api/push/key` (the VAPID public key), `POST /api/push/subscribe` (a PushSubscription's toJSON; 400 unless a push service's), `/unsubscribe` `{ endpoint }`, `/test` `{ endpoint }` (that device alone; 404 not subscribed, 502 refused). What's sent comes from HA's `frame14_notify`, never from a route.
- `GET /api/speedtest/ping` (204 at once), `GET /api/speedtest/download?bytes=` (that many random bytes as octet-stream, `no-store, no-transform`; 16 MiB by default, at most 128 MiB a request; 400 unless a whole number above zero), `POST /api/speedtest/upload` (reads the body, keeps none, `{ bytes }`).
- `GET /api/connection` (the caller's address as seen, the server, the HA link); `GET /api/weather`, `/api/home/weather` (now, 8 h, 24 h, up to 10 days); `/api/home/climate`, `/api/home/fan`, `/api/home/vacuum` (+ `/map/:entityId`, its own maps only).
- `GET /api/home/calendar` (today + tomorrow), `/api/home/calendar/agenda?days=14` (≤ 31; HA's all-day `end` is the day after).
- `GET /api/energy`, `/today` (quarter hours, `selfConsumed`), `/monthly?month=`, `/yearly?year=`; `/api/circuits` (Emporia Vue). `GET /api/printer/camera/stream`, `/api/printer/cover`.
- `GET /api/camera/hls?entity=` (configured cameras only; the master playlist under `/api/camera/hls/<token>/…`, which proxies HA's allow-listed HLS files), `/api/camera/snapshot`, `/api/camera/stream` (MJPEG, unused by the client).
- `GET /api/marquee/art?v=` — the poster: Plex's transcoder at 1280x1920 by ratingKey with PLEX_*, else the entity picture. The client never supplies a URL.
- `GET /api/photos/config` (`defaultAlbumId`, the frames' album, and `options`, `immich_album_ids`), `POST /api/photos/config { option }` (one of them, kept in photos.json, `photos_refresh` to all; 400 another, 404 without albums), `GET /api/photos/albums` (the configured albums named by HA), `/albums/:id` (a configured album's pictures as HA's media source lists them — newest taken first, at most 2000, no videos; 404 another album), `/asset/:id/thumbnail?size=` (preview or thumbnail from HA's `/immich` view; 404 for a photo no configured album's listing named). Without albums: no album, POST 404, the rest 503; HA down 503, HA's Immich failing 502.
- `GET /api/assist/config`, `/api/assist/tts/:id` (ids minted server-side). `GET /api/change/:view` — `change_view` to all clients (HA automations).
- `GET /api/screen` (state, schedule, brightness, dark, auto, lux), `GET /api/screen/:state` (`on` / `off` to every frame), `GET /api/screen/brightness/:level` (0–255, turns auto off), `PUT /api/screen/schedule` / `/dark` / `/auto` (saved and applied; 400 when not a valid setting).

Adding an endpoint: the handler in a `routes/*.js` file, mounted in index.js (more specific paths first: `/api/home/climate` before `/api/home`), documented in openapi.js (its test fails otherwise). Adding an entity id: `frame14.json`, `config.yaml` options + schema, read in `entities.js` onto `ENTITIES`, used from there.

## Socket.IO

- `entity:subscribe` / `entity:unsubscribe` join `entity:<id>` rooms; the server sends the cached state and then acks (also with no state). HA's `state_changed` fans out to the rooms. `entity:call` acks `{ ok }` or `{ ok: false, error }`.
- `change` → `change_view` to the **other** clients; `GET /api/change/:view` → all. The server sends `current_view` on connect. SocketViewListener ignores views on /control and on a remote (a remote goes only where its user takes it).
- `screen` (a command, never re-sent) and `brightness` go to frames' `window.fully`; frames send `brightness_report` and `lux_report`; the server sends `screen_state` on connect and after every change.
- `nav_visibility`: the frames' setting; remotes relay it but keep their own nav.
- Theme: `theme_mode` / `theme_palette` from the Display card, kept by theme.js and broadcast; `current_theme_mode` / `current_theme_palette` on connect.
- Photos: `photos_refresh` (POST /api/photos/config picked an album) reloads every slideshow; a frame emits `photo_shown`; everyone gets `photos_shown`; a remote's `show_photo { albumId, assetId }` is broadcast and frames save it as the album's position. No view change goes with it.
- Voice: `assist:start` (ack), `assist:audio` (Int16LE PCM), `assist:audio_end`, `assist:cancel`; the server emits `assist:event` (TTS path swapped for an opaque `audioUrl`; `intent-end` carries `cue` — a non-null cue plays a tone instead of speech, judged for LLM turns by the tool results in `intent-progress`, since an LLM labels every reply `action_done`) and `assist:error`. One run at a time.
- `echo` with an ack: the connection menu's round trip; socketWake's liveness check.
- `entities`: the entity payload again when the rooms or Unraid change. `ready` (server restart) reloads.
- People (0.168.0): the server reads the handshake's Access token (never holding the handshake up for it) and, for a person it names, keeps `socket.data.user`, joins the socket to the `signed-in` room and counts it as their presence (the handshake's `auth.device` is the kind of device); `people` — the list, each row's alias with it — goes to that room alone as someone comes or goes, or an alias changes. A socket Access didn't name hears nothing of it.

## Security

No login of its own, by the user's choice — anything that reaches the port can use it; the LAN side is left open deliberately and access from outside goes through Cloudflare Access. Don't propose a login, a LAN allow-list or Tailscale unprompted. What the server guards:
- `HA_TOKEN` never reaches a browser; every picture and stream is proxied, and the client never supplies a URL or an entity the server didn't derive (printer, cameras, marquee, vacuum maps, TTS).
- origin-guard.js refuses a browser's request from another site — Sec-Fetch-Site `same-site` / `cross-site` (another app under the same Cloudflare domain counts), else an Origin that isn't the Host's or X-Forwarded-Host's — on all of /api (403) and the socket's handshake; requests with no browser headers (HA's `rest_command`, curl) pass.
- `entity:call` is held to an allow-list of domains, services and argument shapes in ha-socket.js's `callService`, and every entity to one a page shows (`callableEntity`): a light the pages show (`hooks.lights` — index.js hands startHaSocket ha-areas.js's `lightsConfig().lights`, the configured lights and the rooms'; the configured ones without it) or the printer's chamber light; a switch via `callableSwitch` (the configured `light_entities` switches and the chamber light — never Unraid's array, VM or container switches); a configured fan (`fan_entities`) or thermostat (`climate_entities`); `media_player` only `play_media` of this HA's TTS on `assist_speaker`; vacuums and printer buttons only the configured devices with checked arguments; a scene, script or automation only one `scene_entities` names (`sceneCallData`), by the one service that runs it — `scene.turn_on`, `script.turn_on`, `automation.trigger` with `skip_condition` (Home Assistant's "Run actions") — never an automation's turn_off or toggle. A page that calls a new kind of entity needs it added there, or the call is refused. `tests/server/callable-entity.test.js` and ha-socket.test's refusals cover it.
- The Unraid page is read only: no start, stop or update, by the user's word.
- Photos: only the configured albums' pictures (photos.js serves an asset only once a listing of one of `immich_album_ids` has named it; ids are UUIDs, the account is HA's).
- The speed test's routes hold nothing of the house's: they send random bytes (128 MiB a request at most) and count and drop what they are sent, for whoever reaches the port — the same open LAN as everything else, and behind origin-guard like all of /api.
- Who is signed in (0.168.0) is Cloudflare Access's word, read and checked, not a login: nothing is refused to a caller it didn't name (the home network, the frame, `rest_command`). A name is taken only from a token signed by the configured team's keys — a header is anyone's to write on the LAN — and the names go only to callers who are named themselves (`/api/account`'s `people`, the socket's `signed-in` room). The one address the server calls for it is the team's own keys page, built from the option, never from a token. An alias (0.173.0) is set only by a caller who is named, on a row there is — text held to a line's length, drawn as text — and `[account:alias]` logs who set it.
- Push subscriptions are the one URL a page hands the server to call: push.js takes only the browsers' push services' endpoints (https, PUSH_HOSTS), and a tap's `url` is held to an app path.

## Home Assistant add-on

- The folder is `frame14/`; the Supervisor finds the add-on by its `slug`, `frame14`. **Never change `slug`** — every install would see a new add-on and need it installed and configured again.
- `config.yaml` — manifest, options and schema, `url` (this repo; the README's My-HA links use the hash of the URL an instance added). `run.sh` exports scalar options via bashio; arrays are read from options.json by entities.js. `CHANGELOG.md` is the add-on's Changelog tab.
- Ingress is only a doorway: HA's Open Web UI and sidebar load the add-on in an iframe under `/api/hassio_ingress/<token>/`, where the dashboard can't run, so index.js serves `routes/ingress.js` alone on `ingress_port` and it moves the whole tab to `web_ui_url`. With `host_network: true` that port is on the HA host.
- `ha-automation.yaml` — example motion automation. The repo root's `README.md` is the add-on's GitHub page (official add-on README shape: badges, My-HA buttons, every option, the pages, security, local development); keep its options and pages current.

## Standing decisions (don't undo without asking)

Each of these was the user's call; most guard against a design they rejected.
- **Home climate card**: plain wide rectangles everywhere. **/climate**: squares on a phone only (the temperature at the square's centre, the status centred at the bottom; the reading at SQUARE_TILE_READING, light 300 — the weight the user settled on), `lg` tiles on the frame and desktop. Rejected: squares everywhere; dials on /climate.
- No desktop system footer (tried and removed — don't propose it back). No floating header bar (the header stays attached).
- The desktop lights strip was deleted; revive it from git tag `v0.144.1` only if asked.
- Drawers are never full height. The modal rules above (sheet / dialog / side panel / full) and the no-blur-on-Android rule.
- The fan and light drawers are the thermostat's dial geared to them; the dial's numbers roll (NumberFlow) and its marker animates on −/+.
- The Weather card opens WeatherDialog rather than the page. The energy detail has the page's Solar and Circuits tabs.
- Settings shows tabs on every device. Remotes are never moved by broadcasts or motion.
- The Software card: the versions are the links to their releases (no separate GitHub button); install progress is indeterminate (the Supervisor never filled in a percentage); the release notes are in the confirm dialog, not the card.
- Toasts are outlined (bg.panel, a border in the type's colour), always closable, and in the bottom-right corner. Progress bars are fully rounded and brand blue unless the colour is a warning.
- Every card casts the navs' shadow (none in the Outlines palette, and an inner one in Embossed, which presses the cards in: both the user's asks). Embossed presses the dial in as well, inside its ring (0.169.3) — and the navigation with the cards, as from the start (0.172.0, "Make the navigation concave also": it stood up for one version, 0.171.3).
- Buttons and segmented controls have the tiles' inner corner (`sm`, a thermostat tile's), not the cards' own and not pill ends (0.169.1, correcting 0.169.0's "same border radius as cards"); progress bars stay fully rounded. Cards and both navs share `bg.surface` and the `surface` radius; tiles inside are concentric (`sm`).
- Everything pressable goes in under the finger at contact, shaded, and springs back; a tap ticks where the device can (0.170.0). The press is lib/press's `data-pressing`, not `:active`; an iPhone ticks through a hidden switch, the only way Safari leaves, laid by the `ios-haptics` library (0.170.1, the user's choice over our own code for it: "a maintained library").
- /home doesn't scroll on the frame, a tablet or a desktop: every card stays on the board, cut under a row or folded to its header where it must be, and whatever is cut opens out whole from its "+N more" (0.171.0) — a full row to tap, a finger's height on the wall, not a caption (0.171.1). Not pages of cards, not a card that scrolls inside itself, not a board scaled down. A phone scrolls.
- In Embossed the cards are pressed in and the buttons stand up out of them — the light, scene, thermostat and fan tiles, and every button with a face (the mic, the power button, All off, a remote's Views) — and go from pushed out to pushed in while held (0.171.1). Raised is a cast shadow alone: no line of light or shade inside the button's edge, and in Embossed every tile and outline button is the header buttons' colour with no outline (0.171.2, "All buttons should be the same style and color as the header buttons"). The tiles were pressed in with the cards for 0.170.0–0.171.0; the dial still is. And what is only read is a well, pressed into its card: the forecasts' hours and days, the Unraid page's container and VM tiles and the Account card's signed-in rows (0.172.0) — the look the user picked ("Go with A"): the wells' grey floor and no outline.
- A header's lit icon glows while one of its lights is on — /lights' own header, its Favorites and every room, and Home's Lights card: a feathered halo of the icon, fading in and out slowly (0.172.0). The tiles' own icons don't: the user circled the headers'.
